# 공부 방법 — 공개 모델을 7단계로 뜯어보기

논문은 "읽는" 것이지만 공개 모델은 **만질 수 있다.** 이 문서는 모델 하나를 정해 놓고 바깥(문서)에서 안(가중치)으로, 결과(가중치)에서 과정(학습)으로 들어가는 순서를 정리한다.

핵심 원칙 세 가지
1. **작은 것부터.** 70M~135M 모델에서 배운 것은 70B 모델에도 그대로 적용된다. 구조가 같고 숫자만 다르다.
2. **예측하고 확인한다.** 셀을 실행하기 전에 "파라미터가 몇 개일까", "이 층의 shape은?"을 먼저 적는다.
3. **문서의 숫자를 직접 대조한다.** 모델 카드에 적힌 파라미터 수, 논문의 손실 값을 내 손으로 다시 계산해 본다. 맞으면 이해한 것이고, 안 맞으면 거기에 배울 것이 있다.

## 전체 지도

| 단계 | 하는 일 | 걸리는 시간 | 필요한 것 | 산출물 |
|---|---|---|---|---|
| 1 | 문서 읽기: 모델 카드·논문에서 "무엇이 공개됐나"와 숫자 수집 | 1~2시간 | 브라우저 | 공개 수준 체크리스트, 사양 표 |
| 2 | 가중치 열어 보기: 설정·shape·파라미터 수 | 1~2시간 | CPU | 층별 파라미터 표 |
| 3 | 한 토큰이 만들어지는 과정 따라가기 | 2시간 | CPU | 토큰화 → logits → 확률 → 샘플링 기록 |
| 4 | 작은 규모로 직접 학습하기 | 3~5시간 | CPU (GPU면 더 좋음) | 손실 곡선, 체크포인트, 모델 카드 |
| 5 | 학습 과정 관찰하기: 체크포인트 비교 | 2시간 | CPU | 학습 단계별 손실·생성 예시 |
| 6 | 바꿔 보기: 미세조정 | 2~3시간 | CPU (작은 모델) | 전후 비교 |
| 7 | 재 보기: 평가 재현과 오차 막대 | 2~3시간 | CPU | 신뢰구간이 붙은 평가표 |

각 단계의 결과는 [모델 해부 노트](../_templates/model_study.md)의 같은 번호 절에 적는다.

---

## 1단계 · 문서 읽기 (모델 카드와 논문)

**목표:** 코드를 열기 전에 "이 모델은 무엇이고, 무엇이 공개됐는가"를 한 장으로 정리한다.

**하는 일**
1. [공개 수준 체크리스트](01_openness-levels.md#4-판별-체크리스트-모델-하나에-10분) 10문항에 답한다.
2. 아래 **사양 표**를 채운다. 논문·모델 카드·`config.json`에서 찾는다.

| 항목 | 찾는 곳 | 예: Pythia-70m |
|---|---|---|
| 구조 | 논문 모델 절, config | 디코더 전용 Transformer (GPT-NeoX) |
| 층 수 / 폭 / 헤드 수 | config, README 표 | 6 / 512 / 8 |
| 파라미터 수 | 모델 카드 | 약 7천만 (임베딩 포함 기준) |
| 문맥 길이 | config (`max_position_embeddings`) | 2,048 |
| 어휘 크기 / 토크나이저 | tokenizer 설정 | 약 5만 / BPE |
| 학습 데이터 / 총 토큰 수 | 논문 데이터 절 | the Pile / 약 3,000억 토큰 |
| 옵티마이저 / 학습률 / 배치 | 논문 부록, 설정 파일 | 학습률 1e-3, 배치 2M 토큰 |
| 체크포인트 | 저장소 | 154개 (step 0, 1, 2, 4, …, 1000, 이후 1,000마다) |
| 주요 평가 결과 | 논문 표 | (논문에서 직접 찾아 적기) |

3. 논문은 [워크북](../00_Foundations/10_paper-reading-workbook.md)의 방식으로 읽되, 모델 논문에서는 다음 세 가지를 특히 찾는다.
   - **데이터 표**: 어떤 출처가 몇 %인가
   - **학습 설정 표**: 다음 단계에서 설정 파일과 대조할 숫자들
   - **ablation**: 저자가 "이걸 빼면 나빠진다"고 보인 요소

**확인 질문:** 이 모델의 "토큰당 파라미터 수"(총 학습 토큰 ÷ 파라미터 수)는 얼마인가? 다른 모델과 비교하면?

---

## 2단계 · 가중치 열어 보기

**목표:** 가중치 파일이 "이름 붙은 숫자 배열들의 모음"임을 눈으로 확인하고, 파라미터 수를 직접 맞춰 본다. → [lab01](labs/lab01_inspect_open_model.ipynb) 1~2절

**하는 일**
1. `config.json`을 열어 1단계의 표와 대조한다.
2. 모든 파라미터의 이름과 shape을 출력한다. 반복되는 블록 하나의 구성을 파악한다.
3. **손으로 계산**: 임베딩(어휘 × 폭) + 블록당 파라미터 × 층 수 + 마지막 정규화. 모델 카드의 숫자와 일치하는가?
4. 어느 부분이 파라미터를 가장 많이 차지하는지 비율을 구한다.

**확인 질문**
- 작은 모델에서는 임베딩이 전체의 큰 비율을 차지한다. 왜인가? 모델이 커지면 이 비율은 어떻게 되나?
- 입력 임베딩과 출력층이 가중치를 공유(weight tying)하는가? 파라미터 수 계산에서 어떻게 드러나는가?

---

## 3단계 · 한 토큰이 만들어지는 과정 따라가기

**목표:** "텍스트 → 토큰 → 벡터 → 층을 통과 → logits → 확률 → 다음 토큰"을 중간값을 꺼내 보며 따라간다. → [lab01](labs/lab01_inspect_open_model.ipynb) 3~5절

**하는 일**
1. 문장을 토큰화하고 토큰 조각을 눈으로 본다. 한국어와 영어의 토큰 수를 비교한다.
2. 모델의 출력 logits에서 마지막 위치의 상위 10개 토큰과 확률을 본다.
3. temperature를 바꿔 분포가 어떻게 변하는지 본다. greedy와 샘플링의 결과를 비교한다.
4. `generate()`를 쓰지 않고 **직접 루프를 돌려** 토큰을 하나씩 붙여 본다.
5. 층별 은닉 상태에 출력층을 바로 적용해(logit lens) "몇 번째 층쯤에서 답이 정해지는지" 본다.
6. 어텐션 가중치를 그려 본다.

**확인 질문:** 같은 프롬프트를 두 번 넣었는데 답이 다르다. 어느 단계에서 무작위성이 들어가는가?

---

## 4단계 · 작은 규모로 직접 학습하기

**목표:** 데이터 준비부터 가중치 저장까지를 **한 번 완주**한다. 규모는 작아도 과정은 대형 모델과 같다. → [lab02](labs/lab02_train_tiny_gpt_end_to_end.ipynb)

**하는 일**
1. 텍스트를 준비하고 train/validation으로 나눈다.
2. 토크나이저를 정하고(글자 단위 또는 BPE) 토큰 배열로 바꾼다.
3. 모델을 정의한다. 2단계에서 본 구조를 직접 코드로 쓴다.
4. 학습 루프를 돌린다: 배치 뽑기 → 손실 → 역전파 → 갱신. 학습률 스케줄과 기울기 클리핑을 넣는다.
5. train 손실과 validation 손실을 함께 기록하고 그린다.
6. 체크포인트를 저장하고, **새 프로세스에서 다시 불러** 같은 출력이 나오는지 확인한다.
7. 내 모델의 모델 카드를 쓴다(데이터, 설정, 손실, 한계).

**그다음 단계** (선택)
- [nanoGPT](https://github.com/karpathy/nanoGPT)의 셰익스피어 글자 모델: 저장소 README의 CPU용 명령으로 몇 분이면 된다. `model.py`(구조)와 `train.py`(학습 루프)를 lab02의 내 코드와 한 줄씩 대조한다.
- [nanochat](https://github.com/karpathy/nanochat)의 `runs/runcpu.sh`: 토크나이저 학습 → 사전학습 → SFT → 채팅까지의 축소판.
- GPU 노드를 빌릴 수 있다면 nanochat `runs/speedrun.sh`: README에 따르면 8×H100에서 2시간 안팎에 GPT-2 수준의 모델이 나온다.

**확인 질문**
- 초기 손실은 얼마여야 하는가? (힌트: 어휘 크기가 V이면 균등 분포의 교차 엔트로피는 ln V)
- validation 손실이 train 손실보다 낮게 나온다면 무엇을 의심해야 하는가?

## 5단계 · 학습 과정 관찰하기

**목표:** 최종 가중치가 아니라 **학습 도중의 모델들**을 비교해 능력이 생기는 순서를 본다. 완전 공개 모델에서만 할 수 있는 공부다. → [lab03](labs/lab03_checkpoints_finetune_eval.ipynb) 1절

**하는 일**
1. Pythia-70m의 체크포인트 여러 개(예: step 0, 1000, 10000, 143000)를 `revision="step1000"` 식으로 불러온다.
2. 같은 문장들에 대한 손실을 체크포인트별로 재서 그래프로 그린다.
3. 같은 프롬프트의 이어 쓰기를 체크포인트별로 비교한다. 무엇이 먼저 생기는가(철자·문법 → 흔한 표현 → 사실 관계)?
4. 4단계에서 내가 저장한 체크포인트로도 같은 일을 한다.

**확인 질문:** 학습 step 0의 모델은 어떤 손실을 내는가? 4단계의 "초기 손실" 계산과 일치하는가?

**더 나아가기:** SmolLM2·SmolLM3의 중간 체크포인트 저장소, OLMo 2 1B의 early-training 체크포인트, Olmo 3의 단계별(사전학습 → 중간학습 → 긴 문맥 → SFT → DPO → RL) 체크포인트로 같은 비교를 할 수 있다.

## 6단계 · 바꿔 보기: 미세조정

**목표:** 이미 학습된 가중치를 내 데이터로 조금 바꾸고, 무엇이 얼마나 바뀌는지 본다. → [lab03](labs/lab03_checkpoints_finetune_eval.ipynb) 2절

**하는 일**
1. 작은 과제 데이터(수십~수백 개)를 만든다.
2. LoRA로 미세조정한다. 학습되는 파라미터가 전체의 몇 %인지 센다.
3. 미세조정 전후의 출력을 같은 입력으로 비교한다.
4. 원래 잘하던 것을 여전히 잘하는지도 확인한다(망각).

**확인 질문:** LoRA의 rank를 키우면 무엇이 달라지는가? 전체 미세조정과 비교해 무엇을 잃고 무엇을 얻는가?

---

## 7단계 · 재 보기: 평가 재현

**목표:** "좋아졌다"를 숫자로, 그리고 **불확실성과 함께** 말한다. → [lab03](labs/lab03_checkpoints_finetune_eval.ipynb) 3절, [LLM Lab 03](../04_NLP_LLM/labs/lab03_llm_eval_error_bars.ipynb)

**하는 일**
1. 평가 문항을 고정한다(학습에 쓴 것과 겹치지 않게).
2. 모델별 정답률과 표준오차, 신뢰구간을 구한다.
3. 두 모델을 비교할 때는 문항별 짝지은 차이로 분석한다.
4. 논문의 평가 숫자 하나를 골라 같은 설정으로 재현해 본다. 표준 도구는 [lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness)다. 숫자가 다르면 프롬프트 형식·few-shot 수·채점 방식의 차이를 찾는다.

**확인 질문:** 내 평가 문항이 50개라면 정답률 10%p 차이는 유의한가?

## 컴퓨터 사양별 경로

| 환경 | 할 수 있는 것 | 권장 |
|---|---|---|
| 노트북 CPU만 | 1~7단계 전부 (lab01~03), nanoGPT 글자 모델, 70M~360M 모델 추론 | 이 폴더의 기본 경로 |
| 무료 Colab (T4 GPU) | 위 전부를 더 빠르게 + 1B~3B 모델 추론, 작은 모델 LoRA | SmolLM3-3B, OLMo 2 1B 추론 |
| GPU 1장 (24GB급) | 7B 모델 추론(양자화), nanochat 축소 설정 학습 | Olmo 3 7B 추론, nanochat d12 실험 |
| GPU 노드 대여 (8×H100, 몇 시간) | nanochat speedrun 완주 | "처음부터 끝까지 내가 학습한 채팅 모델" |

비용을 쓰기 전에 **CPU 경로를 먼저 끝내는 것**을 권한다. 큰 모델에서 막히는 지점의 대부분은 작은 모델에서 미리 겪을 수 있다.

## 기록하는 법

- 모델 하나당 [모델 해부 노트](../_templates/model_study.md) 한 개. 이 폴더 아래에 `YYYY-MM-DD_모델이름/` 폴더를 만들고 `model_study.md`로 저장한다.
- 그 모델의 논문·보고서를 정독했다면 같은 폴더에 `summary.md`(14개 질문)도 둔다.
- 실험은 "바꾼 것 → 예측 → 결과 → 해석" 네 칸으로 한 줄씩 남긴다. 실패한 실험도 적는다. ([Marin](https://github.com/marin-community/marin) 프로젝트가 실패까지 공개 기록하는 방식을 참고할 만하다.)
- 대화로 해결한 질문은 `qna.md`에 쌓는다.
